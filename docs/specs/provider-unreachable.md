# Provider unreachable

Amends [agent-session-usage-and-hangs](agent-session-usage-and-hangs.md) and SDD §50 (failure handling). Closes GitHub issue #61.

## What it does
A transient failure to reach the model provider from inside the sandbox, for example a DNS lookup that answers `EAI_AGAIN`, used to end the run as `IMPLEMENTATION_FAILED` after the CLI spent about 6.8 minutes in its own backoff, with 0 tokens used and no cause in the post. Factoree now classifies the failure, ends the session early, retries it, and names the cause when the run fails.

## Decisions
- An `api_retry` event (`{"type":"system","subtype":"api_retry"}`, which Claude Code writes during its backoff) counts only when `error_status` is null. A non-null status (429, 529, any other) is the provider answering, so the CLI's own backoff handles it and Factoree never counts it. — A null status is the CLI failing to reach the provider; any status means the provider was reached.
- Provider text is read from one extracted text field, never from the serialized line: a plain (non-JSON) line, the `result` of a `result` event with `is_error: true`, and the first text block of an `assistant` message (or its plain string `content`) when that text starts with `API Error:`. The text must also carry a connectivity code (`EAI_AGAIN`, `ENOTFOUND`, `ECONNRESET`, `ETIMEDOUT`), or the opencode phrase `Can't reach the API server`, which counts on its own. Tool inputs, `tool_use` blocks, `tool_result` and `user` events, quoted or embedded text, and every other JSON field are never scanned. — Only the CLI's own error is evidence; the same strings appear in code the agent writes and in the output of tools that reach a blocked host.
- The fast-fail reads whole lines only. The tail of an output starts at a line break, and a trailing fragment with no line break is not classified until it is finished, so a cut JSON line never falls back to plain-text classification. — A character slice can cut a long JSON event and turn its inner text into a false match.
- The opencode shape is detected only as far as the stream proves it: the phrase in a plain line and in the message of an `error` event (`error.data.message`, `error.message`). No captured opencode outage stream exists, so this shape is unconfirmed, and it is not widened until a redacted stream is added as a fixture. — Detection of a shape nobody observed would be a guess.
- A match sets `failureKind: "PROVIDER_UNREACHABLE"` on the result, and the summary keeps the API error text, or a synthesized line naming the provider when only null-status `api_retry` events were written. After the process ends, a provider-error line counts wherever it appears and a connectivity retry counts as the last signal; the post-exit check and the live check share one classifier. — The cause is in the output, and the runner is the one place that reads it.
- Fast-fail needs consecutive connectivity events: a run of at least 3 null-status `api_retry` events, or one string provider error, with no other complete non-blank event between them. Any other complete event (assistant, user, tool result, result, another system subtype, a non-null-status retry, plain output) clears the run and the pending deadline; blank-only output counts as none. — One transient retry before a long turn must not cancel a healthy session, because the Claude runner streams only complete messages and a long turn is quiet.
- The deadline is the time Factoree saw the first event of the run, plus `PROVIDER_UNREACHABLE_GRACE_MS` (60 seconds). A later retry in the same run does not move it. The run timeout is checked before the fast-fail, and the fast-fail before the silence limit. When the deadline passes, the runner cancels the process and returns the result at once as `unreachable`. — The CLI writes a retry after each failed try, sooner than the grace, so a deadline that each retry moved forward would never pass and the session would burn the whole backoff.
- Stdout and stderr each keep their own run and deadline, and the earlier deadline fires. New stdout model activity (a complete event that is neither a connectivity retry nor a provider error) also clears the stderr state, because it proves the CLI works again. Output from one stream never arms the other. — A stale error in one stream must not keep a working session armed.
- Rate limits and overload (429, 529) are never an outage: Factoree waits out the CLI's own backoff under the silence limit. — The provider answered, so "could not reach the model provider" would be false.
- Retry ladder, per step and per role: the first failure starts a fresh agent session in the same sandbox (retry 1); the second starts a fresh session in a fresh sandbox (retry 2); the third ends the run with `PROVIDER_UNREACHABLE`. The cap per series is 2 retries, and the first series uses the retry numbers 1 and 2. — A fresh session fixes a stuck CLI, and a fresh sandbox fixes a resolver fault of one sandbox.
- The fresh sandbox applies to the Implementer, and only while no repair has run, because a fresh sandbox starts from the base commit and would drop earlier work. The Refiner, the User Validator and the Reviewer start a fresh session on the second retry too: their sandboxes hold no agent state to lose, and the check sandbox is rebuilt by its own activity. — Dropping work is worse than reusing the sandbox.
- A provider failure that follows the one fresh session after a hang gets its own retries. After a hang the fresh session carries no retry number, and its own series continues from the numbers of the first series, so it uses 3 and 4. The Implementer counts its own retries (0 to 2) in the workflow, and a hang resumes through the continued session in the next attempt, so a hang resume cannot reuse an outage key. — The hang recovery stays at one, an outage is not read as three failures after one, and no key or file repeats within a step.
- The fresh sandbox is rebuilt from the effective work input of the run: the PR head and the merge flag of a PR follow-up run, the sibling repositories, the targets of a change set, the frozen context, and the images, comments and links of the work item. The old work sandbox is released before the fresh one is built. — A rebuilt sandbox must hold the same change as the one it replaces, and the run must not hold a fourth live sandbox against its hold of three.
- The release of the old work sandbox is best effort. A release that fails after Temporal's retries (an `ActivityFailure`, never a cancellation and never another error) is logged once, naming the old sandbox and a capped cause, and the run continues, because the next preparation releases the superseded sandbox. Any other failure, including a failure of the calls around the release, still ends the run as it does today. — A recoverable release fault is not a fault of the run.
- The fresh sandbox keeps the frozen skill resolution. It re-delivers the exact pinned name, version and digest, verifies every archive and the resolution id, never calls `skills.replace` for it, and keeps the activation flags. When the registry cannot serve the pins, or the product names no registry, the run fails as a skill-resolution fault and never takes a newer resolution. A registry skill that a repository skill of the same name shadows is not recorded with its pin, so its resolution can be delivered again only while the registry defaults still give the recorded id. No registry call changes the stored resolution. — A run is judged against the skills it froze, not against what the registry holds later.
- A retry never uses the repair budget, unlike a hang. Every role, the Implementer included, carries an `unreachableRetry` number into its row keys and into the names of its result, proposal, plan, report and re-check files and directories, so a retry never reads the output of a rejected session. The `attempt` ordinal counts only real attempts and repairs (the Proof Pack reads `attempt`). Retry-0 keys keep their old shape, so stored rows stay valid. — A provider fault is not a fault of the change, and it must not inflate the attempt count.
- The Refiner and the Validator send no missing-output reminder once the provider is unreachable. The Validator's resume does not start a fallback session after an outage, and its plan correction and its selector re-check pass the outage up as a provider failure, not as a rejected plan. The Refiner's limit correction does the same. Every correction key (`planCorrectionSessionKey`, `selectorRecheckSessionKey`, `refinerLimitCorrectionSessionKey`) carries `unreachableRetry`. — A fresh fallback session after an outage fails the same way and burns the budget.
- A Reviewer that runs out of retries, in the parallel review or in the triage of PR findings, ends the run with `PROVIDER_UNREACHABLE`. It is never read as "no findings", never spends a repair, and never lets an unreviewed change publish. — An unreviewed change must not publish.
- The failure reason `PROVIDER_UNREACHABLE` has the category `INFRASTRUCTURE`. — It stays off the `AGENT` panel, because the agent did nothing wrong.
- The failure message names the role and the agent error, for example `API Error … EAI_AGAIN`. The provider detail is trimmed and capped at 1,000 characters for every role, with `none reported` for a blank one. The Refiner and the Reviewer keep this provider-specific outcome and are not turned into `REFINEMENT_UNAVAILABLE` or `REVIEW_UNAVAILABLE`. The `IMPLEMENTATION_FAILED` message carries the agent output too, capped the same way. — The Proof Pack and the Linear post show the cause without opening Temporal, and stay bounded.
- `AgentSession.outcome` gets the value `unreachable`, and the role totals count `unreachable` beside `hung`. The value is part of the admin API: the product sessions route lists it from the one domain list of outcomes, `api/openapi.json` and the UI types are generated from that route, and the UI shows a distinct tone. `proof-pack.json` carries `unreachable` in the role totals, as it carries `hung`; the rendered text does not repeat it. — No migration: the column is a plain string. The totals stay machine-readable.
- The workflow gates every new path with the patch `provider-unreachable`. A change of the integer that an activity input carries needs no extra patch, and adding, removing or reordering an activity call does. — A running history replays as before.

## Out
- The root cause of the sandbox resolver or egress fault.
- The mismatch between the stage duration and the session duration.
- Capture of an opencode outage stream: it stays open until a redacted fixture exists.
- Re-resolving skills for any reason other than a fresh sandbox.
- Changing the CLI's own backoff.
