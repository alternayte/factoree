# Provider unreachable

Amends [agent-session-usage-and-hangs](agent-session-usage-and-hangs.md) and SDD §50 (failure handling). Closes GitHub issue #61.

## What it does
A transient failure to reach the model provider from inside the sandbox, for example a DNS lookup that answers `EAI_AGAIN`, used to end the run as `IMPLEMENTATION_FAILED` after the CLI spent about 6.8 minutes in its own backoff, with 0 tokens used and no cause in the post. Factoree now classifies the failure, ends the session early, retries it, and names the cause when the run fails.

## Decisions
- The runner scans the output of a session that did not finish for the agent CLI's own provider error. The scan is JSON aware, because the CLIs stream newline-delimited JSON events. A line counts as a provider error when it is a Claude Code `{"type":"system","subtype":"api_retry"}` event (the CLI retries the provider during its backoff and writes no error text; `error_status: null`, `error: "unknown"`), or when its text carries the CLI marker `API Error` together with a connectivity code (`EAI_AGAIN`, `ENOTFOUND`, `ECONNRESET`, `ETIMEDOUT`), or the opencode phrase `Can't reach the API server`. A `tool_result` or `user` event is skipped before any text match, so a tool that echoes `API Error … ETIMEDOUT` from a blocked host is not read as the agent's provider. A match sets `failureKind: "PROVIDER_UNREACHABLE"` on the result, and the summary keeps the API error text, or a synthesized line naming the provider when only `api_retry` events were written. — The cause is in the output, and the runner is the one place that reads it. A string scan alone misses Claude's backoff, whose events name no code; a code or marker on its own is not enough, because `npm install`, a test, or a tool result that reaches a blocked egress host echoes the same strings, and those are ordinary failures, not a provider outage. (Supersedes the earlier string-only scan, which never fired for the Claude CLI.)
- When the last signal line of the output is such an error for `PROVIDER_UNREACHABLE_GRACE_MS` (60 seconds), the runner cancels the process and returns the result at once. A later line that is model activity, a `result`, a tool result or a user turn resets or is skipped, so a session that recovered is not cancelled. A string provider error counts wherever it appears; an `api_retry` event counts only as the last signal line, because the CLI writes one per retry and a run that recovered then failed on the change must not read as an outage. Stdout and stderr are judged separately, and blank-only output counts as none. — The grace is far under the backoff of the CLI, so the budget stays for the retry, and a healthy session that logged a tool's `ETIMEDOUT` before a long quiet turn is not cancelled.
- Retry ladder, per step and per role: the first failure starts a fresh agent session in the same sandbox; the second starts a fresh session in a fresh sandbox; the third ends the run with `PROVIDER_UNREACHABLE`. — A fresh session fixes a stuck CLI, and a fresh sandbox fixes a resolver fault of one sandbox.
- The fresh sandbox applies to the Implementer, and only while no repair has run, because a fresh sandbox starts from the base commit and would drop earlier work. The Refiner, the User Validator and the Reviewer start a fresh session on the second retry too: their sandboxes hold no agent state to lose, and the check sandbox is rebuilt by its own activity. — Dropping work is worse than reusing the sandbox.
- A provider failure that follows the one fresh session after a hang gets its own retries. Their numbers follow those of the first series, so no key or file repeats. — The hang recovery stays at one, and an outage is not read as three failures after one.
- The fresh sandbox is rebuilt from the effective work input of the Run, with the PR head and the merge flag of a PR follow-up run and the sibling repositories the first work input carried. The old work sandbox is released before the fresh one is built. — A rebuilt sandbox must hold the same change as the one it replaces, and the Run must not hold a fourth live sandbox against its hold of three.
- A retry never uses the repair budget, unlike a hang. Every role, the Implementer included, carries an `unreachableRetry` number into its row keys and into the names of its result, proposal, plan and report files, so a retry never reads the output of a rejected session and the `attempt` ordinal still counts only real attempts and repairs (the Proof Pack reads `attempt`). The Refiner and the Validator send no missing-output reminder once the provider is unreachable, and the Validator passes an outage in its plan correction or its selector re-check up as a provider failure, not as a rejected plan. — A provider fault is not a fault of the change, and it must not inflate the attempt count.
- The failure reason `PROVIDER_UNREACHABLE` has the new category `INFRASTRUCTURE`. — It stays off the `AGENT` panel, because the agent did nothing wrong.
- The failure message names the role and the agent error, for example `API Error … EAI_AGAIN`. The `IMPLEMENTATION_FAILED` message now carries the agent output too. — The Proof Pack and the Linear post show the cause without opening Temporal.
- `AgentSession.outcome` gets the value `unreachable`, and the role totals count `unreachable` beside `hung`. — No migration: the column is a plain string.
- The workflow gates the new paths with the patch `provider-unreachable`. — A running history replays as before.

## Out
- The root cause of the sandbox resolver or egress fault.
- The mismatch between the stage duration and the session duration.
